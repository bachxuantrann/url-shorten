# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

The git root contains a single Maven project in `url-shortener/` (plus a stray root `.idea/`). Run all commands below from `url-shortener/`.

Stack: Java 21, Spring Boot 4.1.1, PostgreSQL, Redis, JWT (jjwt), MapStruct + Lombok. Base package `com.auradev.url_shortener`. Comments and Javadoc are written in Vietnamese; match that when editing existing files.

## Commands

Use the Maven wrapper (`mvnw.cmd` on Windows, `./mvnw` elsewhere).

```bash
# Start local infra (Postgres, Redis, Kafka, Kafka UI on :8090) - the app itself runs from the IDE / mvnw
docker compose -f docker-compose.dev.yml up -d

./mvnw spring-boot:run                 # runs with the `dev` profile (default in application.yaml)
./mvnw clean package -DskipTests       # build the jar
./mvnw test                            # all tests
./mvnw test -Dtest=ClassName#method    # single test

# Full prod stack (app built from Dockerfile + infra); needs a real .env.prod
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

Integration tests use Testcontainers (Postgres, Redis, Kafka via `src/test/.../support/TestcontainersConfiguration`, add `@Import` to the test class), so they need a running Docker daemon but **not** the dev compose, and never touch the dev database. The first run pulls images and is slow; Spring caches the context, so keep test classes on the same configuration to share one set of containers.

### Deployment shape (Phase 9)

`docker-compose.prod.yml`: **Caddy is the only service with published ports (80/443)**; the app uses `expose`, so nothing reaches it without passing Caddy's rate limits and HTTPS. `caddy/Dockerfile` (build context = git root, `docker build -f url-shortener/caddy/Dockerfile .`, ignore file `Dockerfile.dockerignore` next to it) is multi-stage: Vite build of `frontend/`, Caddy 2.11.7 built with `xcaddy` plus `mholt/caddy-ratelimit` pinned by commit (the plugin has no usable release), and `caddy validate` at build time. `caddy/Caddyfile` routes `/api/*` and short links to `app` (dynamic DNS upstream, so replicas/redeploys are picked up), a fixed list of UI paths to the static files (SPA fallback), and answers 404 for `/actuator/*`. Per-IP limits per minute (env `RATE_LIMIT_*`, no rebuild): api 240, auth 15, unlock 30, anon-create 20, redirect 600; Caddy's 429 has `Retry-After` and an empty body, the UI handles that. They sit in front of the Redis limits of the app, which still apply. A new UI route must be added to `@ui` in the Caddyfile **and** to `ShortCodes.RESERVED`. The app sees the real client IP only because Caddy is on the same private Docker network (`X-Forwarded-For` is trusted from private ranges only). `SITE_ADDRESS` (domain or `http://localhost` for a local test without TLS) and `ACME_EMAIL` are required; `APP_BASE_URL` must be the matching https URL. ## Architecture

Layered Spring MVC REST API under `/api/v1` (`auth`, `users`, `admin`; path constants in `AppConstant`): `controller` -> `service` (interface) / `service/impl` -> `repository` (Spring Data JPA). DTOs live in `dto/request` and `dto/response`; entity <-> DTO conversion goes through MapStruct mappers (`mapper/`, component model `spring` set in `pom.xml`).

Annotation-processor order in `pom.xml` matters: Lombok, then `lombok-mapstruct-binding`, then MapStruct. Keep that order when touching the compiler plugin.

### Auth flow (spans several files)

Stateless JWT, no sessions, no `UserDetailsService`. See `SecurityConfig`, `JwtAuthenticationFilter`, `AuthServiceImpl`, `JwtService`, `TokenRedisService`.

- Each login creates a random `sessionId`; both access and refresh tokens carry it (claim `sid`). Multiple concurrent sessions per user are supported.
- Refresh tokens are stored in Redis as `RT:{userId}:{sessionId}`. Refresh compares the presented token to the stored one exactly.
- Logout blacklists the access token by `jti` (`BL:{jti}`, TTL = remaining lifetime) and deletes that session's `RT:` key. There is currently no "logout all devices".
- `JwtAuthenticationFilter` builds authentication purely from JWT claims (userId, username, roles) and never hits the DB, so a **role** change only takes effect when the access token expires. **Account lock is immediate** though: `AdminServiceImpl.lockUser` writes `LOCK:{userId}` in Redis (TTL = access token lifetime + 1 min, `TokenRedisService.markUserLocked`), the filter asks Redis (`isUserLocked`, O(1), no DB) and, when set, leaves the request unauthenticated with request attribute `ACCOUNT_LOCKED_ATTRIBUTE`; the `SecurityConfig` entry point then answers **403 `ERR_104`** (`ACCOUNT_BANNED`) instead of 401 (a 401 would make the client try to refresh). `unlockUser` clears the marker. Refresh tokens are deliberately NOT deleted on lock: refresh and login already reject `BANNED` users with `ERR_104` from the DB status, so someone who comes back after a long idle still learns why (covered by `AccountLockIntegrationTest`). Otherwise the filter never throws: an invalid token just leaves the request unauthenticated, and Spring Security returns 401.
- `AppConstant.PUBLIC_ENDPOINTS` is the permit-all list; `/api/v1/admin/**` requires `ROLE_ADMIN`; everything else needs authentication. Method security (`@PreAuthorize`) is enabled.

### URL domain (Phase 1)

`Url` entity (table `urls`, extends `BaseEntity`) is managed by `UrlController` -> `UrlService`/`UrlServiceImpl` under `/api/v1/urls` (authenticated; ownership via `userId`). Links of other users or with status `DELETED` are always reported as `URL_NOT_FOUND` (404). `BLOCKED` links cannot be modified/disabled/deleted by their owner. Status rules live in `UrlServiceImpl` (see its Javadoc); `EXPIRED` is only revived by an update with a new expiry.

Short codes: `ShortCodeGenerator` turns the next value of the Postgres sequence `short_code_seq` (`UrlRepository.nextShortCodeSequence`) into a 7-char Base62 code via a keyed Feistel permutation with cycle walking, so codes are unique by construction (bijection) and not guessable/countable. The key is `app.shortener.code-secret` (env `SHORT_CODE_SECRET`) and **must stay constant across deploys**. `app.shortener.base-url` (env `APP_BASE_URL`) builds `shortUrl` in responses. URL content checks (http/https, host present, no userinfo, max 2048) are in `UrlUtils`; target safety rules (SSRF, loops, blocklist) are in `UrlTargetPolicy` (see Abuse protection). List sorting is whitelisted in `UrlController` (`createdAt`, `clickCount`, `expiresAt`). `GET /api/v1/urls?keyword=` searches the owner's links by partial, case-insensitive match on `originalUrl` or `shortCode` (max 100 chars; `%`, `_` and `!` are escaped by `UrlServiceImpl.toLikePattern` and treated literally; combinable with `status` and paging).

### Redirect path (Phase 2)

Public `GET /{code}` (`RedirectController` -> `RedirectServiceImpl`) answers `302` + `Location` + `Cache-Control: no-store` (302 and no-store so link changes apply immediately and every click can be counted later). `SecurityConfig.redirectRequestMatcher()` permits any single-segment GET/HEAD path made of code characters that is not in `ShortCodes` reserved words (`/api`, `/actuator`, `/admin`... stay authenticated); the 3-32 length rule is enforced in the service so bad codes get a JSON 404 instead of 401. Add new top-level routes to `ShortCodes.RESERVED`.

Status mapping: unknown / malformed / reserved / `DISABLED` -> 404 (`URL_NOT_FOUND`), expired (`EXPIRED`, or `ACTIVE` past `expiresAt`) / `DELETED` -> 410 (`URL_GONE`), `BLOCKED` -> 403 (`URL_ACCESS_BLOCKED`).

Lookup is Redis cache-aside then Postgres (`UrlCacheService`, key `URL:{code}` = `STATUS|expiresAt|protected|originalUrl` or `MISSING` for negative caching (see Link extras for the `protected` field); TTL `app.shortener.cache-ttl` capped at time-to-expiry, `negative-cache-ttl` for misses). Redis errors are swallowed and treated as a cache miss, so a Redis outage never breaks redirects. **Any code path that changes a link's status, target or expiry (including future admin block, expiry job, alias changes) must call `UrlCacheService.evictAfterCommit(code)`**; tests that change a row directly through the repository must call `evict`. A tiny race (reader loads DB just before a commit, writes cache just after the eviction) can leave a stale entry for at most `cache-ttl`.

### Link lifecycle (Phase 3)

Expiry is enforced **lazily at redirect time** (`RedirectServiceImpl` compares `expiresAt` with the clock), so correctness never depends on a job. `UrlExpirationJob` (`@Scheduled`, every `app.shortener.expiry-job-interval`, default `PT1M`, declared in `application-dev/prod.yaml` along with the cache TTLs and batch size; disable with `app.shortener.expiry-job-enabled=false`) only syncs state by moving `ACTIVE` links past `expiresAt` to `EXPIRED` through `UrlExpirationService.expireBatch` (one transaction per batch of `app.shortener.expiry-batch-size`, default 500). A batch is **one SQL statement** (`UrlRepository.expireDueLinks`: `WITH due AS (... FOR UPDATE SKIP LOCKED) UPDATE ... RETURNING short_code`), so statements do not grow with the number of links (a regression test counts them; an entity-by-entity version issued N+1). Multi-instance safety comes from `SKIP LOCKED` (each instance claims different rows), not from a distributed lock. Because it is a bulk update, JPA auditing does not run and the query sets `updated_at`/`updated_by` (`system`) itself; cache keys are evicted with a single Redis `DEL` via `UrlCacheService.evictAllAfterCommit`. Only `ACTIVE` links are touched: `DISABLED`/`BLOCKED`/`DELETED` keep their status.

`UrlServiceImpl.toResponse` reports an `ACTIVE` link past its `expiresAt` as `EXPIRED` so the API matches redirect (410) before the job runs; the `status=` list filter still filters on the stored status. Deleted links are soft-deleted (`status=DELETED`, `deletedAt`) and their code is never reused.

Time: inject the `Clock` bean (`AppConfig`) and use `LocalDateTime.now(clock)` for anything involving link expiry or cache TTL, so tests can use `Clock.fixed`. Surefire sets `app.shortener.expiry-job-interval=PT24H` so the scheduler never fires during the suite; `UrlExpirationSchedulingTest` overrides it to `PT1S` to prove the scheduling wiring.

### Abuse protection (Phase 4)

- **Anonymous links:** `POST /api/v1/public/urls` (`PublicUrlController`, public) creates a link with `userId = null` (`createdBy = anonymous`). Nobody owns it, so only an admin can block it. A valid/invalid token on that endpoint is ignored.
- **Rate limiting:** `RateLimitService` (Redis fixed window, one atomic Lua script `INCR`+`EXPIRE`, key `RL:{bucket}:{subject}`), rules in `RateLimitProperties` (`app.rate-limit.anonymous-create` per client IP, default 10/h; `user-create` per user id, default 100/h; `limit <= 0` disables). Exceeding throws `RateLimitExceededException` -> HTTP 429 + `Retry-After` (`GlobalExceptionHandler`). Every request counts, including ones rejected for a bad URL. It **fails open** when Redis is down. The client IP is `request.getRemoteAddr()` (`ClientIpUtils`); `server.forward-headers-strategy: native` lets Tomcat swap in `X-Forwarded-For` **only when the peer is a trusted proxy** (private/loopback ranges), so internet clients cannot spoof it; never read that header manually. Integration tests rely on this by sending `X-Forwarded-For` from loopback to get independent counters.
- **Per-user quota:** `app.shortener.max-links-per-user` (default 1000, `<= 0` = unlimited) counts non-deleted links with one `COUNT` (not locked, so concurrent creates can overshoot by a few) -> `URL_QUOTA_EXCEEDED` (403).
- **Target policy** (`UrlTargetPolicy`, run on create **and** update, after `UrlUtils.validate`): (1) own host (host of `base-url` + `app.shortener.own-hosts`) -> `UNSAFE_URL_TARGET` (redirect loops); (2) unless `block-private-targets=false`, localhost, private/loopback/link-local (cloud metadata) / reserved IPv4 in any notation, private IPv6, `.local`/`.internal`/... names and single-label hosts -> `UNSAFE_URL_TARGET`; (3) `blocked_domains` (host or any parent domain, one query) -> `BLOCKED_DOMAIN`. `HostUtils` is purely syntactic and **never resolves DNS**, so a public name that resolves to a private IP is not detected; that is acceptable only while the server never fetches target URLs itself. If a feature starts fetching URLs server-side (link preview, malware scan) it must re-check the resolved IP.
- **Admin moderation** (`ROLE_ADMIN`, `/api/v1/admin/**`): `GET/PUT /urls/{code}[/block|/unblock]` (block needs a reason, stored in `urls.blocked_reason`; unblock sets `ACTIVE`; the owner sees `status=BLOCKED` + reason but cannot modify it) and `POST/GET/DELETE /blocked-domains` (`POST` can also block every existing `ACTIVE/DISABLED/EXPIRED` link of that domain with one `UPDATE ... RETURNING` using `HostUtils.urlHostRegex`; removing a domain does **not** unblock links already blocked). Block/unblock and bulk blocking evict the redirect cache after commit.
- Admin ops use the actor's username for `updated_by` (entity updates via auditing; the bulk statement via `AuditorAwareImpl`).
- **Admin link list** (`GET /api/v1/admin/urls?keyword=&status=&page=&size=&sortBy=&sortDir=`, `AdminUrlController` -> `AdminUrlService.list` -> `UrlRepository.findAllForAdmin`): every non-deleted link of everyone incl. anonymous; keyword (max 100) matches target, short code or `createdBy` (username or `anonymous`) through `LikePatterns.contains` (shared with the owner's search; wildcards escaped); sort whitelist `createdAt|clickCount|expiresAt` plus `id` as tiebreaker so paging is stable; an `ACTIVE` link past `expiresAt` is reported `EXPIRED` (same rule as the owner API). JSON omits null fields, so anonymous links have no `userId`. Two statements per page regardless of size (proved in `AdminUrlListIntegrationTest`). The backend does not stop an admin from locking their own account (`PUT /admin/users/{id}/lock`), the UI just disables that button.
- **Abuse reports** (V10 `abuse_reports`, `AbuseReportService`): anyone reports a link with `POST /api/v1/public/reports` `{shortCode, reason: SPAM|PHISHING|MALWARE|ILLEGAL|OTHER, details<=500}` (`PublicReportController`). Per-IP limit `app.rate-limit.report-per-ip` (5/h, `RateLimitProperties.reportPerIp`, in both profile yamls; every request counts); the code format is checked before any DB access. The reporter is stored only as `VisitorHasher.reporterHash(ip)` (HMAC with `CLICK_VISITOR_SECRET`, **no day** in the input so the same person is recognised across days; raw IP never stored); `UNIQUE (url_id, reporter_hash)` + `INSERT ... ON CONFLICT DO NOTHING` (`AbuseReportRepository.insertIfNew`) means one report per person per link, a repeat answers 201 and changes nothing (a plain JPA insert would abort the transaction). Unknown/malformed/reserved/deleted code -> 404 `ERR_400`; an already `BLOCKED` link answers 201 and stores nothing. Admin (`AdminReportController`, `/api/v1/admin/reports`): `GET ?status=OPEN|RESOLVED|DISMISSED` returns **one row per link** (count, last report, per-reason counts, link status; 3 statements per page: grouped page, count, reasons via `IN`, proved constant in `AbuseReportApiIntegrationTest`), `GET /{code}` lists the individual reports (max 100, no reporter identity), `PUT /{code}/resolve|dismiss` close all OPEN reports of the link in one bulk `UPDATE` (sets audit columns itself) and return how many. `AdminUrlServiceImpl.blockUrl` closes the link's OPEN reports as `RESOLVED` in the same transaction; the bulk domain block does **not** (reports of links blocked that way stay OPEN until dismissed or resolved by hand).

- **Appeals of blocked links** (V11 `link_appeals`, `LinkAppealService` owner side, `AdminAppealService` admin side): the owner of a `BLOCKED` link sends `POST /api/v1/urls/{code}/appeal` `{message<=500}` (`UrlController`; per-user limit `app.rate-limit.appeal-per-user` 5/h, in both profile yamls, every request counts, validation errors do not). Not the owner/deleted -> 404 `ERR_400`; link not blocked -> 409 `ERR_402`; an appeal already waiting -> 409 `ERR_412` (`APPEAL_ALREADY_OPEN`). One OPEN appeal per link is enforced by the partial unique index `uq_link_appeals_open` plus `INSERT ... ON CONFLICT (url_id) WHERE status = 'OPEN' DO NOTHING` (`LinkAppealRepository.insertIfNoneOpen`, same trick as abuse reports, proved with 4 simultaneous requests), so a double submit is a clean 409 and never aborts the transaction. `UrlResponse.appeal` (`AppealInfoResponse`: status, message, response, createdAt; null omitted from JSON) is filled by `UrlServiceImpl` in `get` and `list` for BLOCKED links only, with ONE `IN (...)` query per page (`findLatestForUrls`, no query at all when the page has no blocked link; proved constant in `LinkAppealApiIntegrationTest`). Only appeals that still concern the current block are shown: OPEN always; REJECTED only when `appeal.createdAt >= url.updatedAt` (an admin re-block bumps `url.updatedAt`, so an old rejection disappears and a new appeal is allowed); ACCEPTED never (the link is active again). The appeal is written with `LocalDateTime.now(clock)` and compared with Hibernate's `updatedAt`, so a test that fixes the `Clock` far in the past would hide a rejection. Admin (`AdminAppealController`, `/api/v1/admin/appeals`): `GET ?status=OPEN|ACCEPTED|REJECTED` (default OPEN; OPEN oldest first, the others most recently handled first; one JPQL query joining link and owner username + one count, via `AppealRow`), `PUT /{id}/accept` and `PUT /{id}/reject` (body `{response<=255}` optional). Both close the appeal with `UPDATE ... WHERE id = ? AND status = 'OPEN'` (0 rows = 409 `ERR_414` `APPEAL_NOT_OPEN`, so two admins clicking at once cannot both win; unknown id 404 `ERR_413`); accept then calls `AdminUrlService.unblockUrl` in the SAME transaction (cache eviction included). `AdminUrlServiceImpl.unblockUrl` also closes a waiting appeal as ACCEPTED, so unblocking from the links page answers the owner's appeal too. Dependency direction (no cycle): `AdminAppealServiceImpl` -> `AdminUrlService` -> `LinkAppealService`; `UrlServiceImpl` -> `LinkAppealService`. Tests: `LinkAppealApiIntegrationTest` (20). Bruno: `url/appeal blocked link`, `admin/list appeals (admin)`, `admin/accept appeal (admin)`, `admin/reject appeal (admin)`.

- **Role change** (`PUT /api/v1/admin/users/{id}/role` `{role: ROLE_ADMIN|ROLE_USER}`, `AdminController` -> `AdminServiceImpl.changeRole`): ROLE_ADMIN = {ADMIN, USER}, ROLE_USER = {USER}; every user keeps ROLE_USER. An admin cannot change their own role (403 `ERR_107`) and the last ACTIVE admin cannot be demoted (409 `ERR_108`, `UserRepository.countActiveWithRoleExcluding`; needed because a demoted admin's JWT stays valid until it expires). Same role = no-op 200. **Not immediate:** roles live in the JWT, so it takes effect when the user's access token expires (15 min) or they sign in again (the UI dialog says so; the account lock is the only immediate one). ### Link extras (Phase 5)

- **Custom alias:** `CreateUrlRequest.alias` (3-32 chars `[0-9a-zA-Z_-]`, case-sensitive, immutable) becomes `urls.short_code`. Only for logged-in users: the anonymous endpoint uses `CreatePublicUrlRequest` (URL + expiry only) and `createAnonymous` ignores alias/password. Reserved words, taken aliases and aliases of deleted links (codes are never reused) all answer **409 `ERR_407`** with one message; malformed ones are 400 validation errors. `urls.short_code` was widened to 32 chars in V6 to match `ShortCodes.MAX_LENGTH`.
- **Alias vs generated code collision:** a 7-char alias can equal a code the generator produces later. A failed `INSERT` (unique violation `uq_urls_short_code`) aborts the Postgres transaction, so `UrlServiceImpl.createLink` runs each attempt in its **own** `TransactionTemplate` transaction and retries with a fresh code (max 5) from outside; the alias path never retries (it answers 409). Integration-tested on real Postgres. Do not turn `create` back into a single `@Transactional` method. BCrypt hashing also happens outside the transaction.
- **Password-protected links:** `urls.password_hash` (BCrypt via the shared `PasswordEncoder`, input 4-64 chars and at most 72 UTF-8 bytes), set at creation or via `PUT /api/v1/urls/{code}/password`, removed via `DELETE` on the same path (separate endpoints on purpose: `PUT /{code}` replaces target+expiry and must not silently drop protection). Responses only expose `passwordProtected`. `GET /{code}` of a protected link answers **403 `ERR_408`** (status/expiry rules are checked first, so a disabled/expired/blocked link never reveals it has a password). A request whose `Accept` contains `text/html` (a browser) gets **302 `Location: /unlock/{code}`** instead (same-origin UI route, `no-store`, no click); API clients keep the 403 JSON. The UI routes `unlock`, `dashboard`, `links`, `settings`, `profile` (and later `report`, `overview`) are in `ShortCodes.RESERVED`. The client (the UI unlock page) calls **`POST /api/v1/public/urls/{code}/unlock`** `{password}` and receives `{originalUrl}` to navigate to (wrong password 403 `ERR_409`). `unlockTarget` always reads the DB and checks status/expiry before spending CPU on BCrypt.
- **The cache never holds a protected link's target or hash:** value is `STATUS|expiresAt|protected|originalUrl` (`protected` = `P` or `-`, URL empty when `P`); old 3-field entries are treated as misses. Setting/removing a password evicts the cache like any other change.
- **Unlock brute-force limits** (`RateLimitProperties`, checked in `PublicUrlController` in this order): per IP 30/15 min, per (link, IP) 10/15 min, per link 100/h; exceeding gives 429 + `Retry-After`. The code format is validated before any limiter key is created so invented codes cannot create unbounded Redis keys. Known trade-off: exhausting the per-link budget (needs many IPs) delays legitimate unlocks of that link for up to an hour.
- **QR codes:** `GET /api/v1/urls/{code}/qr?size=` (owner only, 404 otherwise) returns a PNG of `{base-url}/{code}` generated on the fly by `QrCodeGenerator` (ZXing core, error correction M, quiet zone 4, size clamped to 128-1024, default 320, `Cache-Control: private, max-age=3600`). Nothing is stored. Tests decode the PNG with ZXing (`support/QrDecoder`) to prove it scans.

### Click tracking (Phase 6)

Flow: successful `GET /{code}` (`RedirectController`) or correct `POST /api/v1/public/urls/{code}/unlock` (`PublicUrlController`) -> `ClickPublisher.publish` -> Kafka topic `url-clicks` (key = `shortCode`) -> `ClickEventConsumer` (batch) -> `ClickIngestService.ingest` -> table `url_clicks` + `urls.click_count`. Never emitted for 403/404/410 (including `ERR_408`) or for `HEAD` requests.

- **Producer never blocks a redirect.** `KafkaClickPublisher` reads IP/User-Agent/country header on the request thread, then hands the send to the bounded `clickPublishExecutor` (`KafkaConfig`, `AbortPolicy`): a full queue drops the event (`droppedCount()`), a failed send is counted (`failedCount()`), nothing is thrown. The producer also has `max.block.ms=500`, `request.timeout.ms=2000`, `delivery.timeout.ms=5000` in the profile yaml. `KafkaClickPublisherTest` proves it against a dead port.
- **`spring-boot-starter-kafka`** replaced plain `spring-kafka` in `pom.xml`: without it Boot 4 had no Kafka auto-configuration and every `spring.kafka.*` property was silently ignored. `ClickEvent` is serialized to a JSON string with the app's Jackson 2 `ObjectMapper` (String (de)serializers stay).
- **Topics** `url-clicks` and `url-clicks.DLT` are declared as `NewTopic` beans (`app.click.partitions`, `replicas`). The broker auto-creates single-partition topics, so do not rely on that.
- **Privacy:** no raw IP anywhere (not in Kafka, not in the DB). `VisitorHasher` = `HMAC-SHA256(secret, day|ip|userAgent)` cut to 32 hex chars (`app.click.visitor-secret`, env `CLICK_VISITOR_SECRET`, required in prod). Day is in the input, so "unique visitor" only means unique within one day. Changing the secret only breaks unique counts once (unlike `code-secret`).
- **Enrichment:** device/browser/OS are parsed in the consumer by `UserAgentParser` (uap-java for browser and OS, normalized to one name, e.g. "Chrome Mobile" -> `Chrome`; device type MOBILE/TABLET/DESKTOP/BOT is derived by our own rules because uap-java has none; bots are stored as device `BOT`, not dropped, and still counted in `click_count`). Country comes from `GeoIpService` (MaxMind GeoLite2-Country `.mmdb`, path `app.click.geoip-database` / env `GEOIP_DATABASE`, empty = country null, set-but-missing file = startup failure, read once at startup so restart after updating the file). The lookup runs in the **producer** on the request thread (an in-memory file read) because events carry no IP; only the 2-letter code goes into the event. Client headers such as `CF-IPCountry` are ignored. The `.mmdb` file is not in the repo (needs a free MaxMind account and a mount in the container); `GeoIpServiceTest` runs the real lookup only when env `GEOIP_TEST_DB` points to a file.
- **Idempotent batch write:** `UrlClickRepository.insertBatch` is one SQL statement per batch (arrays `unnest`ed, `INSERT ... ON CONFLICT DO NOTHING RETURNING url_id`, then `UPDATE urls SET click_count = click_count + n` from the returned rows), so a redelivered event is neither stored nor counted twice. PK is `(event_id, clicked_at)` and `clicked_at` is the event's own time. `ClickIngestServiceImpl` resolves codes to ids with one `IN (...)` query (soft-deleted links still resolve; unknown codes are logged and skipped). This statement does **not** touch `urls.updated_at`/`updated_by` on purpose (a click is not an edit of the link).
- **Errors:** malformed messages (bad JSON, missing fields, eventId not a UUID) go straight to `url-clicks.DLT` and are skipped; infrastructure errors (DB down) bubble up to `DefaultErrorHandler` (exponential back-off, max 15 s) and then the whole batch goes to the DLT (`DeadLetterPublishingRecoverer`). Nothing consumes the DLT yet.
- **Partitions:** `url_clicks` is range-partitioned by month (`url_clicks_yYYYYmMM`) with a `url_clicks_default` partition so an out-of-range click is never lost. V7 creates this month + 3 more; `ClickPartitionJob` (every `app.click.partition-job-interval`, default `PT6H`, surefire sets `PT24H`) calls `ClickPartitionService.maintain`: creates `partition-months-ahead` months and drops partitions older than `retention-months` (13; `<= 0` keeps all). Multi-instance safe through `pg_try_advisory_xact_lock`. If the default partition already holds rows of a month, Postgres refuses to create that month's partition (logged, other months still proceed).
- Tests: `ClickTrackingIntegrationTest`, `ClickPartitionIntegrationTest` (real Postgres/Redis/Kafka), `KafkaClickPublisherTest`, `UserAgentParserTest`, `VisitorHasherTest`. Kafka-listener tests use Awaitility and unique short codes; "was not recorded" assertions wait 1.5 s after a sentinel click.

### Click analytics (Phase 7)

- **Daily stats, one statement.** The same SQL statement that stores a click batch (`UrlClickRepository.INSERT_SQL`) also upserts `url_daily_stats (url_id, stat_date)` (`clicks`, `bot_clicks`, `unique_visitors`), inserts new human visitors into `url_daily_visitors (url_id, stat_date, visitor_hash)` and adds to `urls.click_count`. Every delta is computed from the rows actually inserted (`RETURNING`), so redelivery never double counts and the counters cannot drift apart. `stat_date` is the server-local date of `clicked_at`.
- **Unique visitors are exact per day, not an estimate.** A visitor is "new" for (link, day) when its row in `url_daily_visitors` is inserted (`ON CONFLICT DO NOTHING`), which is also correct under concurrent instances (tested with 4 threads). Bots (device `BOT`) and events without a `visitor_hash` are never unique visitors. Because the hash includes the day, the total over a range is a sum of daily uniques (a person returning on 2 days counts twice); the API says so. Trade-off: `url_daily_visitors` holds one row per unique human per link per day, deleted after `retention-months` by `ClickPartitionServiceImpl` (aggregates in `url_daily_stats` are kept forever). If it ever gets too big, replace it with Redis HyperLogLog (approximate) or partition it by month.
- **Lock ordering:** the CTEs insert in `ORDER BY` order so concurrent batches lock rows in the same order. Two batches updating the same `urls` row can still wait on each other; a rare deadlock is retried by the Kafka error handler and the batch is idempotent.
- **Stats APIs:** `GET /api/v1/urls/{code}/stats` (owner; other users' and deleted links are 404) and `GET /api/v1/admin/urls/{code}/stats` (admin; any non-deleted link incl. anonymous), `?from=&to=` as `yyyy-MM-dd`, inclusive, default last 30 days, max 366 days (`INVALID_STATS_RANGE`, `ERR_411`, 400; a malformed date is 400 `VALIDATION_FAILED`). Response (`UrlStatsResponse`): `totals`, zero-filled `daily`, and top-10 `countries` / `browsers` / `operatingSystems` (human clicks only, unknown country = `Unknown`) and `devices` (includes `BOT`). `UrlStatsServiceImpl` issues a constant 3 statements: link lookup, `url_daily_stats` range read, and one `GROUPING SETS` scan of `url_clicks` for all four breakdowns (so breakdowns only cover the raw-data retention window; the daily series is permanent). There is no cross-link/account-wide overview yet.
- **Account overview:** `GET /api/v1/stats/overview?from=&to=` (`StatsController`, authenticated; base path `/api/v1/stats` on purpose so it can never be shadowed by a user alias under `/api/v1/urls/...`) returns `StatsOverviewResponse` for **all of the caller's non-deleted links**: `links` (counts by status; an `ACTIVE` link past `expiresAt` counts as `EXPIRED`, independent of the date range), `totals`, zero-filled `daily`, `topLinks` (top 5 by clicks in the range, links without clicks skipped), and the same top-10 `countries/devices/browsers/operatingSystems` as the per-link API. Same range rules (default 30 days, max 366, `ERR_411`). Four statements regardless of how many links (`UrlStatsRepository.*ForUser` through `JdbcTemplate`; proved in `StatsOverviewApiIntegrationTest` by counting the Micrometer `jdbc.query` timer, since Hibernate statistics cannot see `JdbcTemplate`). Clicks of soft-deleted links are excluded. `overview` is in `ShortCodes.RESERVED`.
- **Reconciliation:** `ClickReconciliationJob` (daily, `app.click.reconcile-*`) calls `ClickReconciliationService`: (1) `urls.click_count` vs `sum(url_daily_stats.clicks)` (against the stats, not `url_clicks`, because raw rows are deleted after retention); (2) `url_daily_stats.clicks` vs raw `url_clicks` for the last `reconcile-window-days` days (report only). Default is detect-and-log; `reconcile-repair=true` (env `CLICK_RECONCILE_REPAIR` in prod) fixes the counters under row locks (`FOR UPDATE` first, then recompute in a fresh statement), so it cannot lose a concurrent increment.
- **Migrations:** V8 creates the two tables, V9 backfills them from existing `url_clicks` (`ClickStatsIngestIntegrationTest` re-runs the V9 script to prove it rebuilds identical rows).
- Tests: `ClickStatsIngestIntegrationTest`, `ClickReconciliationIntegrationTest`, `UrlStatsApiIntegrationTest`. Bruno: `url/get link stats`, `admin/get link stats (admin)`.

- `logback-spring.xml` keeps Boot's defaults and adds the OTel appender; `ObservabilityConfig` installs it, adds Redis (Lettuce) tracing, and drops `/actuator/**` spans. Do not add a `level` to the second `<root>`.
- **One trace per redirect:** HTTP, Spring Security, Redis, JDBC and the Kafka producer span (the send runs on `clickPublishExecutor`, wrapped with `ContextExecutorService` so the observation follows it). The consumer is a batch listener, which Spring Kafka does not observe, so `ClickEventConsumer` makes a `click.ingest` span per batch (CONSUMER, JDBC spans below it) with **span links** to each click's `traceparent` (max 50). `ObservabilityIntegrationTest` proves all of this and that traces, metrics and logs reach a fake OTLP/HTTP collector.
- **Custom metrics** are centralized in `AppMetrics` (`redirect.latency{outcome}`, `url.cache.requests{result}`, `click.events{result}`, `click.ingest.*`); circuit breaker state comes from `resilience4j-micrometer`; Kafka client metrics (including `kafka.consumer.fetch.manager.records.lag.max`) are bound by Boot. Add a new metric there, not inline.

In the Kafka publisher every `tryAcquirePermission` must be paid with exactly one `onSuccess`/`onError`. ### Errors and i18n

All errors go through `AppException(ErrorCode, args...)`. `ErrorCode` holds the code (`ERR_xxx` ranges documented in the enum), message key, and HTTP status. `GlobalExceptionHandler` and the 401/403 handlers in `SecurityConfig` both render the same `ApiResponse` shape, with messages resolved by `TranslatorUtils` from `src/main/resources/i18n/message.properties` and `message_vi.properties`. A new error needs an `ErrorCode` entry and a key in both property files.

### Config

`application.yaml` selects the `dev` profile; `application-dev.yaml` / `application-prod.yaml` hold the rest. Custom settings are bound by `JwtProperties` and `AdminProperties` (`app.jwt.*`, `app.admin.*`). `DataInitializer` creates the admin account from `app.admin.*` at startup. Schema is managed by **Flyway** (`src/main/resources/db/migration`, `V{n}__name.sql`); Hibernate runs with `ddl-auto: validate` in every profile, so every entity change needs a new migration. Never edit an applied migration. Flyway settings live per profile, not in `application.yaml`: dev sets `baseline-on-migrate: true` (adopts a legacy DB as V1, can be dropped once every dev DB has run Flyway); prod sets it `false` so it refuses a non-empty DB with no Flyway history, plus `clean-disabled: true`. Entities that need auditing extend `BaseEntity` (`createdAt`/`updatedAt` via Hibernate, `createdBy`/`updatedBy` via Spring Data auditing and `AuditorAwareImpl`: username, `anonymous` for unauthenticated requests, `system` outside a request). It uses Lombok `@SuperBuilder`, so subclasses must too, and a table for such an entity needs `created_at`, `updated_at`, `created_by`, `updated_by` NOT NULL columns. Bulk `@Modifying`/native update queries bypass auditing, so they must set the audit columns themselves (see `UrlRepository.expireDueLinks`).

## Coding rules

- **Never write code that causes N+1 queries.** The number of SQL statements for an operation must not grow with the number of rows it handles. This covers both N+1 *selects* (loading a collection or association once per row, e.g. a lazy/EAGER association touched inside a loop over query results) and N *writes* (updating or inserting row by row where one statement would do). Check this on every query, loop over entities, mapper that touches associations, and list/paging endpoint you add or change.
- Ways to stay clear of it: `JOIN FETCH` / `@EntityGraph` for associations that are needed, a single `WHERE id IN (...)` query instead of a query per id, projections or DTO queries when you do not need whole entities, one bulk statement (`UPDATE ... WHERE ...`, `INSERT ... SELECT`, `UPDATE ... RETURNING`) instead of mutating entities in a loop, and Redis multi-key commands (`DEL`/`MGET` with a collection) instead of one call per key. If you do need JPA batching for inserts/updates, enable it explicitly (`hibernate.jdbc.batch_size`, `order_inserts`/`order_updates`) and prove it with a test.
- `User.roles` is an `EAGER` element collection. Any query returning several users used to load roles one user at a time (an N+1 found in the admin user list: 3 users = 5 statements, 40 users = 42). It now carries `@BatchSize(size = 100)` (= `AppConstant.MAX_PAGE_SIZE`), so roles of a whole page load in one `IN (...)` query; do not replace this with `JOIN FETCH` on a paged query (Hibernate would paginate in memory). Guarded by `UserRolesQueryCountIntegrationTest`. Any new `@ElementCollection`/`@OneToMany` that is loaded alongside a list of parents needs the same treatment.
- Bulk statements bypass JPA auditing, so they must set `updated_at`/`updated_by` themselves (see `UrlRepository.expireDueLinks`).
- Prove it with a test, do not just reason about it: enable Hibernate statistics at runtime (`entityManagerFactory.unwrap(SessionFactory.class).getStatistics()`, `setStatisticsEnabled(true)`, `clear()`) and assert `getPrepareStatementCount()` stays constant for N = a few vs a few dozen rows. See `UrlExpirationIntegrationTest.expiringManyLinksIssuesAConstantNumberOfStatements`.

## Product direction and development plan

Goal: a TinyURL-style shortener. Currently only auth/user management exists (base project); the URL domain is built in the phases below. Build phase by phase; each phase must be runnable and tested on its own.

### Design decisions (already made)

- `users.id` stays **UUID** (used in JWT claims and Redis keys). `urls.user_id` is a UUID FK, nullable for anonymous links. `urls.id` is `BIGSERIAL`.
- `short_code` is the public identifier (UNIQUE), `id` is internal. Generated codes: DB sequence -> scramble -> Base62 (min 6-7 chars). Custom aliases share the same column, so reserved words (`api`, `swagger-ui`, `actuator`, ...) must be rejected.
- Status enum `UrlStatus`: `ACTIVE`, `DISABLED`, `EXPIRED`, `BLOCKED`, `DELETED`. `expires_at` is separate from `status`.
- Soft delete (`deleted_at`). A short code once issued is **never reused**.
- Redirect uses **302** (301 would be cached by browsers and lose click stats). Responses: expired -> 410, missing -> 404, blocked -> 403.
- Redirect path: Redis cache-aside (with negative caching) -> Postgres fallback if Redis is down. Click tracking is async via Kafka and must never break a redirect.
- Kafka is at-least-once: every `ClickEvent` carries a unique `eventId`; consumers are idempotent (`ON CONFLICT DO NOTHING`).
- Schema is managed by Flyway (replace `ddl-auto: update` with `validate` in Phase 0). `url_clicks` is partitioned by month. Per-country/device stat tables are only added when a dashboard needs them.
